01 The Extraction Model

Three layers, three levels of reuse.

The transition from Claude Code to a web deployment is not a rewrite — it's a decomposition. The existing Vantage engine separates into three layers, each with a different level of reuse and a different amount of new engineering.

Layer 1 — Domain Logic (high reuse)

The Python code that does the actual work

HCC mapping, RAF scoring, population generation, scenario execution, TCOC calculation, measure evaluation. These are pure functions and data pipelines. They don't care whether they're invoked by Claude Code reading a SKILL.md or by a FastAPI endpoint. The DataStore abstraction means the same query() and execute() calls work against DuckDB locally or PostgreSQL/Databricks in production. This layer transfers almost 1:1 — same Python modules, imported and called by tool handlers.

Layer 2 — Orchestration Intelligence (medium reuse)

The domain expertise that knows when and how to use the logic

This is the CLAUDE.md personality — the knowledge that a V28 exposure question needs dual-scoring, that a Triple-Play should check all three domains, that effect weights should be cited with confidence levels. In Claude Code this lives in CLAUDE.md and SKILL.md files as natural language instructions. In the web deployment, this becomes the system prompt for the Anthropic Messages API. The content is identical; the delivery mechanism changes. Custom commands (/simulate, /compare, /report) become tool definitions in the API function-calling schema.

Layer 3 — Infrastructure (new build)

The web plumbing that doesn't exist in Claude Code

A FastAPI server, user authentication, session and conversation state management, SSE streaming, the React frontend, file storage for generated reports, rate limiting, and multi-tenant data isolation. This is genuinely new work, but it's well-understood engineering — FastAPI + React + PostgreSQL is a well-trodden path. None of this requires healthcare domain knowledge; it's standard web application infrastructure.

The Extraction Principle
Domain intelligence transfers as content (system prompt text, reference documents, Python functions). Orchestration transfers as structure (tool schemas, routing logic). The only genuinely new work is infrastructure (web server, auth, session state, frontend). This means the healthcare domain expertise — the hard part — is already built. The web layer is "just" plumbing.

04 System Prompt Construction

CLAUDE.md becomes the system prompt.

The system prompt for the web API is assembled from existing Vantage configuration files. It uses a layered injection pattern — the orchestrator identity is always present, and domain skill context is injected dynamically based on what the conversation requires.

Layered Prompt Assembly

# Python: system prompt assembly in the API server

def build_system_prompt(session: Session, user_message: str) -> str:
    """Assemble the system prompt from Vantage config files.
    
    Layer 1 (always):  Orchestrator identity + routing + conversation patterns
    Layer 2 (always):  Active population context (if one exists)
    Layer 3 (dynamic): Domain skill knowledge, injected by relevance
    """

    # Layer 1 — CLAUDE.md content (verbatim from the repo)
    # This is the ~1,500 token orchestrator identity that includes
    # the three-domain routing table, conversation patterns,
    # confidence interval requirements, and output preferences.
    prompt = Path("config/orchestrator.md").read_text()

    # Layer 2 — Population context (if a population is active in this session)
    if session.population_id:
        pop = get_population_summary(session.population_id)
        prompt += f"""

## Active Population
- ID: {pop.id} | Members: {pop.count:,}
- Geography: {pop.geography} | Mean Age: {pop.mean_age}
- V24 RAF: {pop.v24_raf:.3f} | V28 RAF: {pop.v28_raf:.3f}
- Dual-eligible: {pop.dual_pct:.1f}% | ACO-attributed: {pop.aco_pct:.1f}%
"""

    # Layer 3 — Skill context (injected based on user message relevance)
    for skill_name in route_skills(user_message):
        skill_content = Path(f"config/skills/{skill_name}.md").read_text()
        prompt += f"\n\n## Skill: {skill_name}\n{skill_content}"

    return prompt

Skill Routing — The Lightweight Classifier

In Claude Code, skill routing happens naturally — the agent reads SKILL.md metadata (the YAML frontmatter), decides which skills to load, then reads the full body. In the API, we replicate this with a skill router that classifies the user message and injects relevant skill content into the system prompt.

The simplest implementation is keyword-based. A production version could use a fast Haiku classifier call, or embed the routing table in the orchestrator system prompt and let the model self-select which tools to call (effectively delegating routing to Claude itself).

# Skill routing — mirrors CLAUDE.md's skill routing table

SKILL_ROUTES = {
    # keywords → skill file names to inject into system prompt
    "risk":       ["risk-model"],
    "hcc":        ["risk-model"],
    "raf":        ["risk-model"],
    "v28":        ["risk-model"],
    "v24":        ["risk-model"],
    "coding":     ["risk-model"],
    "stars":      ["quality-model"],
    "quality":    ["quality-model"],
    "hedis":      ["quality-model"],
    "adherence":  ["quality-model"],
    "tcoc":       ["vbc-model"],
    "mlr":        ["vbc-model"],
    "savings":    ["vbc-model"],
    "mssp":       ["vbc-model"],
    "cost":       ["vbc-model"],
    # Multi-domain triggers → inject all three skills
    "invest":     ["risk-model", "quality-model", "vbc-model"],
    "triple":     ["risk-model", "quality-model", "vbc-model"],
    "compare":    ["risk-model", "quality-model", "vbc-model"],
    "simulate":   ["risk-model", "quality-model", "vbc-model"],
}

def route_skills(message: str) -> list[str]:
    """Return deduplicated list of skill names relevant to the message."""
    skills = set()
    msg_lower = message.lower()
    for keyword, skill_list in SKILL_ROUTES.items():
        if keyword in msg_lower:
            skills.update(skill_list)
    return sorted(skills) or ["risk-model", "quality-model", "vbc-model"]  # default: all
Context Window Budget
The full CLAUDE.md orchestrator is ~1,500 tokens. Each SKILL.md body is ~500–800 tokens. Population context is ~200 tokens. A Triple-Play with all three skills uses ~4,000 tokens of system prompt — well within budget for Sonnet or Opus with 200K context. The deep reference documents (references/*.md — V28 model details, hierarchy rules, etc.) are NOT injected into the system prompt. The model accesses that knowledge through tool calls that query reference data in the database.

06 MCP Server Transition

MCP tools become API tool handlers.

In Claude Code, MCP (Model Context Protocol) servers provide data access through a stdio or SSE transport — the agent calls tools like query_population or get_hcc_mapping, and the MCP server process handles the request against DuckDB. In the web deployment, this indirection is replaced by direct function calls within the API server process.

Transport Change

AspectClaude Code (MCP)Web API
Transportstdio (local process) or SSE (remote)In-process function call
Tool schemaMCP tool definition (JSON Schema)Anthropic API tool definition (JSON Schema) — near-identical format
InvocationClaude Code's tool-use loop sends JSON-RPC to MCP serverAPI server intercepts tool_use blocks, calls Python handler
Data accessMCP server process holds DuckDB connectionTool handler calls DataStore through connection pool
ConcurrencySingle-writer (close-before-write pattern)PostgreSQL MVCC handles concurrent access natively

What This Means Concretely

The vantage-data MCP server defined in .claude/settings.json exposes tools like query_table, save_population, get_scenario. In the web version, these become methods on a VantageDataService class that wraps the DataStore. The tool definitions (JSON schemas) are nearly identical — the only difference is the transport layer.

# Claude Code: MCP server tool (in vantage_mcp.py)
@mcp.tool()
def query_table(table: str, filters: dict) -> list[dict]:
    store = DuckDBStore(db_path)
    return store.query(build_sql(table, filters))

# Web API: equivalent tool handler (in tool_handlers.py)
def handle_query_reference_data(table: str, filters: dict, session: Session) -> dict:
    store = get_store(session.tenant_id)  # PostgresStore from pool
    return store.query(build_sql(table, filters))  # Same SQL, same function
The MCP servers you've already built are your tool handler blueprints
Each MCP tool's implementation becomes a tool handler function in the web API. The data access logic, SQL queries, and result formatting are identical. The difference is just how the function gets called — MCP's JSON-RPC vs. the API server's tool-use intercept loop.

Why the web version is structurally better
In Claude Code, everything is a flat text stream. In the web version, the tool result (Step 5) provides structured JSON that the frontend renders into the scenario context panel, domain impact cards, and summary dashboard — while Claude's narrative streams into the conversation panel. The tool results give you data the CLI never had: machine-readable numbers that drive the right panel, confidence bars, and domain breakdowns. The same analysis that produces a text narrative also produces a live dashboard.

The Chat Endpoint — Agentic Loop

The /chat endpoint is the heart of the server. It implements the agentic tool-use loop: send to Claude, receive tool calls, execute handlers, return results, repeat until Claude produces a final text response.

# Simplified agentic loop in the chat endpoint

async def chat_handler(session_id: str, message: str):
    session = await get_session(session_id)
    system = build_system_prompt(session, message)
    messages = session.conversation + [{"role": "user", "content": message}]

    while True:
        response = await anthropic.messages.create(
            model="claude-sonnet-4-20250514",
            system=system, tools=TOOLS, messages=messages,
            stream=True, max_tokens=4096
        )

        async for event in response:
            if event.type == "content_block_delta":
                # Stream text to client
                yield sse_event("text_delta", event.delta.text)

            elif event.type == "content_block_start" and event.content_block.type == "tool_use":
                # Notify client that a tool is executing
                yield sse_event("tool_start", {"tool": event.content_block.name})

        # Check if the response contains tool_use blocks
        tool_uses = [b for b in response.content if b.type == "tool_use"]

        if not tool_uses:
            break  # No more tools — final response complete

        # Execute each tool and collect results
        tool_results = []
        for tool_use in tool_uses:
            result = await execute_tool(tool_use.name, tool_use.input, session)
            tool_results.append({
                "type": "tool_result",
                "tool_use_id": tool_use.id,
                "content": json.dumps(result)
            })
            # Send structured result to client's right panel
            yield sse_event("tool_result", {"tool": tool_use.name, "result": result})

        # Append assistant response + tool results to messages for next loop
        messages.append({"role": "assistant", "content": response.content})
        messages.append({"role": "user", "content": tool_results})

    # Persist updated conversation to session
    await save_session(session_id, messages)

Rate Limiting and Cost Management

Each Anthropic API call has a token cost. The server should track usage per tenant and enforce limits. A single Triple-Play analysis typically uses ~8,000–12,000 tokens (system prompt + conversation + tool results + final response). At Sonnet pricing, that's roughly $0.03–0.05 per analysis. Multi-turn conversations accumulate conversation history, so longer sessions cost more. Consider implementing a conversation history truncation strategy that preserves recent turns and scenario summaries while dropping older raw tool results.

09 Data Layer

DuckDB to PostgreSQL — the DataStore swap.

The DataStore abstraction in packages/core/data_access.py was designed for exactly this transition. The abstract interface defines query(), execute(), load_reference_table(), and save_population(). In Claude Code, DuckDBStore implements these. For the web, PostgresStore replaces it.

Why the Swap Is Necessary

DuckDB's single-writer constraint is the specific reason. In Claude Code, this is manageable with the close-before-write pattern (close read connection, open write connection, write, checkpoint, close). In a web server handling concurrent requests from multiple users, this pattern breaks down — you'd need to serialize all writes globally, which defeats the purpose of a multi-user system. PostgreSQL's MVCC handles concurrent reads and writes natively.

What Changes, What Doesn't

ConcernDuckDB (Claude Code)PostgreSQL (Web)
ConcurrencySingle-writer, close-before-writeFull MVCC, concurrent reads/writes
ConnectionLocal file pathConnection string with asyncpg pool
Multi-tenancyN/A — single userSchema-per-tenant or row-level security
Schema initscripts/init_db.py from CSVsSame CSVs, loaded via COPY or Alembic migration
SQL dialectDuckDB SQLPostgreSQL SQL (highly compatible)
Analytical perfColumnar engine, fast aggregationsRow-store; add indexes. Consider Citus for scale.
SQL Compatibility
DuckDB's SQL dialect is intentionally Postgres-compatible. Most queries — especially reference data lookups and RAF calculations — work unchanged. Adjustments are needed for DuckDB-specific functions (list_aggregate, struct types) which can be rewritten as standard SQL or PostgreSQL equivalents. The DataStore abstraction layer isolates these differences.

SSE Event Protocol

The chat endpoint uses Server-Sent Events to stream both text (for the conversation) and structured data (for the right panel) in a single connection.

# SSE event types from the Vantage API server

# Text streaming → conversation panel (center)
event: text_delta
data: {"delta": "━━ TRIPLE-PLAY SCENARIO: PHARMACIST HTN PROGRAM ━━"}

# Tool execution status → status pills in conversation
event: tool_start
data: {"tool": "run_scenario", "status": "executing"}

# Tool completion with structured data → right panel update
event: tool_result
data: {"tool": "run_scenario", "result": {"risk": {...}, "quality": {...}, "cost": {...}}}

# Report generated → outputs tab update
event: report_ready
data: {"filename": "htn_triple_play.html", "download_url": "/api/reports/rpt_xyz"}

# Stream complete
event: done
data: {}

Frontend State Machine

The frontend maintains a simple state model. When it receives a tool_result event, it updates the right panel with structured data. When it receives text_delta events, it appends to the conversation stream. When tool_start fires, it shows status pills. This gives users the live dashboard experience — numbers appearing in the right panel as analysis runs, while the narrative builds in the center.

// Simplified React state model

const [conversation, setConversation] = useState([]);     // center panel
const [scenarioData, setScenarioData] = useState(null);   // right panel scenario tab
const [activeTools, setActiveTools]   = useState([]);     // status pills
const [reports, setReports]           = useState([]);     // right panel outputs tab

eventSource.onmessage = (event) => {
  switch (event.type) {
    case "text_delta":
      appendToCurrentMessage(event.data.delta);    // stream into center
      break;
    case "tool_start":
      setActiveTools(prev => [...prev, event.data.tool]);
      break;
    case "tool_result":
      setScenarioData(event.data.result);          // update right panel
      setActiveTools(prev => prev.filter(t => t !== event.data.tool));
      break;
    case "report_ready":
      setReports(prev => [...prev, event.data]);   // update outputs tab
      break;
  }
};

If the Claude Code workspace develops HTML dashboard templates or PPTX slide templates, these transfer directly. The templates are just files — they don't care about the runtime. # Report generation handler (same libraries as Claude Code)

async def handle_generate_report(
    format: str, scenario_ids: list, session: Session
) -> dict:
    # Fetch scenario results (same SQL, different DataStore)
    scenarios = await store.query(
        "SELECT * FROM scenarios WHERE id = ANY($1)", [scenario_ids]
    )

    if format == "pptx":
        buf = generate_pptx(scenarios)  # python-pptx, same template
    elif format == "html_dashboard":
        buf = render_html(scenarios)    # Jinja2, same template
    elif format == "pdf":
        buf = generate_pdf(scenarios)   # reportlab or WeasyPrint

    # Upload to S3
    key = f"reports/{session.user_id}/{uuid4()}.{format}"
    await s3.upload(key, buf)
    url = await s3.presigned_url(key, expires=3600)

    # Record in database
    await store.execute(
        "INSERT INTO generated_reports (session_id, format, filename, storage_path) ..."
    )

    return {"filename": filename, "download_url": url}
12 Migration Roadmap

Four phases from CLI to web application.

These phases are sequential but don't block continued development in Claude Code. The local workspace remains the primary development and testing environment. New skills and domain logic are built and validated in Claude Code first, then tool definitions and handlers are added to the web layer.

Phase W1 — API Wrapper (2–3 weeks)

Prove the extraction works

Stand up a FastAPI server. Convert CLAUDE.md → system prompt. Define the first 4 tools (generate_population, score_raf, query_reference_data, run_scenario). Wire a single DuckDB instance behind the DataStore (multi-tenancy comes later). Test the Triple-Play HTN prompt via curl and verify the output matches Claude Code's analytical quality. This is the critical proof point.

Deliverable: A working API that produces the same V28 exposure and Triple-Play analyses as Claude Code, testable via command line.

Phase W2 — Frontend (3–4 weeks)

Build the experience

Build the React frontend from the mockup: three-panel layout, SSE streaming, session management, quick-start prompt buttons. Add remaining tools (evaluate_quality_measures, calculate_tcoc, compare_scenarios, generate_report). Implement basic auth (API keys). Wire the right panel to structured tool results. Wire report downloads.

Deliverable: A demo-able web UI that consulting firm partners can use for the V28 exposure hook and Triple-Play differentiation story.

Phase W3 — Multi-Tenancy (2–3 weeks)

Support real users

Swap DuckDB for PostgreSQL via DataStore abstraction. Implement per-tenant data isolation (schema-per-tenant or row-level security). OAuth user accounts. Rate limiting and usage tracking. S3 report storage. Conversation history truncation strategy for cost management.

Deliverable: A product that external users can sign into and run analyses independently, with data isolation and cost controls.

Phase W4 — Databricks Integration (ongoing)

Enterprise scale

Implement DatabricksStore for customers running against real member populations via Unity Catalog. Same tool definitions, same system prompt, same frontend — different DataStore selected by tenant configuration. Add support for customer-provided effect weight overrides and population imports.

Deliverable: Enterprise customers can connect their Databricks environment and run analyses against real claims data. Vantage becomes strategic infrastructure, not just a simulation tool.

The Parallel Track
The Claude Code workspace continues in parallel through all web phases. It remains the fastest environment for developing new skills, testing domain logic, and running one-off analyses. The web version lags by one "sync cycle" — new capabilities land in Claude Code first, then get tool definitions and handlers added to the web layer. Think of it as: Claude Code is dev, the web is prod.
