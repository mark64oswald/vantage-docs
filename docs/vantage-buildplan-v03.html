1 Build Philosophy

Deliverables first, models second.

The central lesson from planning to this point: build toward shareable artifacts, not toward model completeness. A V28 exposure analysis report that a consulting firm can hand to a client — with methodology, caveats, and a Vantage attribution — does more to create market momentum than a technically complete simulation engine that produces no output anyone outside the project has seen.

Every phase is organized around a primary deliverable: a concrete output that could be put in front of a potential customer. The underlying model development serves the deliverable, not the other way around.

The V28 Urgency Window
The V24→V28 transition is creating industry-wide demand for exposure analysis right now. MA plan CFOs are asking "what's our V28 exposure?" at every strategy meeting. Phase 1 is timed to this window: produce a credible, shareable V28 dual-scoring report before the question becomes old news. The consulting channel can walk this deliverable into client meetings today.

The secondary principle is solo-developer economics. This is a one-person build with Claude Code as co-developer. Phases are scoped for months, not quarters. Complexity is introduced only when a deliverable requires it. The effect weight calibration challenge — getting the causal relationships between levers and domains right — is real but tractable: Claude can directly support the literature synthesis needed to populate reference.effect_weights with documented weights, uncertainty ranges, and source citations.

4 Phase 1 In Depth

What to build first, and in what order.

Phase 1 is the only phase where sequence matters enough to be prescriptive. The goal is to get to a runnable V28 exposure analysis as fast as possible — not because it's technically impressive, but because it's the deliverable that can start a market conversation.

Recommended Build Sequence

Before Phase 1 Starts: Phase 0 Cleanup
Complete the Execution Guide Phase 0 Cleanup steps first. This takes ~30 minutes and ensures the scaffold is in clean, accurate shape before any Phase 1 code is written. Don't skip it.
Week 1–2: Data Foundation
Start with the reference data, not the code. Load CMS-published V24 and V28 HCC crosswalk files and RAF coefficient tables into DuckDB. Write and validate the ICD-10 → CC → HCC mapping logic against CMS published examples. This is the foundation everything else rests on — if the crosswalk is wrong, all downstream calculations are wrong.
Week 2–3: HealthSim Harvest + Population Engine
Fork the HealthSim population generation module (structural patterns: seed management, parameter validation, bulk-insert). Build out the MA-specific domain content: age/sex distribution, geographic distribution (county FIPS from reference.county_demographics), condition prevalence, and HCC assignment. Validate that generated population-level RAF scores fall within expected ranges for a real MA population.
Week 3–4: Risk Model Core
Implement the RAF scoring logic in the risk-model skill. Inputs: population.members + population.member_hccs + reference.hcc_crosswalk + reference.raf_coefficients. Outputs: output.member_raf with V24 and V28 scores per member. Validate individual member scores against CMS published Ratebook examples before moving to aggregation.
Week 4–5: Delta Analysis + Report
Build the V24/V28 delta analysis (HCC reclassifications, coefficient changes, net revenue impact by HCC category). Build the HTML report template: population summary, dual-score comparison, revenue impact, top HCC exposure categories, concentration analysis. This is the deliverable — invest time in making it look credible and methodology-transparent.
Week 5–6: Parallel — Effect Weight Synthesis
While the report template is being refined, begin populating reference.effect_weights with literature-sourced effect weights for Phase 2 levers (CDM, coding programs, pharmacy). Claude can directly support this synthesis. Having documented weights with uncertainty ranges and source citations ready before Phase 2 starts avoids a bottleneck.

Phase 1 Testing Strategy

Phase 1 tests are verification tests, not statistical tests. The CMS V24 and V28 Ratebook files contain published RAF scores for specific member profiles — use these as ground truth. If a 70-year-old female with HCC 18 (Diabetes w/ Chronic Complications) in the CNA segment does not score the published RAF value under V24 and the equivalent under V28, something is wrong.

Key Test Cases
HCC mapping accuracy: specific ICD-10 codes → expected CC/HCC under V24 and V28 (CMS published crosswalk as ground truth). RAF scoring: specific member profiles → expected RAF scores from CMS Ratebook. Hierarchy application: a member with both HCC 17 and HCC 18 (diabetes hierarchy) should only count the more severe. Dual-scoring delta: a member with HCC 85 (CHF) should show the expected V24→V28 coefficient change. Dual enrollment / new enrollee segments: confirm correct segment assignment and coefficient tables used.

8 Development Principles

How to work, not just what to build.

01

Deliverable First, Then Model

Every sprint should end with something a potential customer could see. Design the Phase 1 report template before writing the RAF scoring code. Design the Phase 2 Triple-Play output before wiring up the scenario runner.

02

Validate Before Extending

Each layer of the stack must be validated against published CMS examples before the next layer is built on top of it. Wrong HCC crosswalk → wrong RAF score → wrong revenue impact. Catch it at the crosswalk.

03

Honest Uncertainty

Every simulation output should surface its confidence level. The effect weight library stores low/base/high ranges. Reports show confidence intervals, not point estimates. Credibility comes from acknowledging what isn't known.

04

Fork, Don't Rewrite

HealthSim's population generation and DuckDB patterns are proven. Fork the structural patterns. Leave HealthSim-specific logic behind. Don't spend Phase 1 time rebuilding what already works.

05

PHI Zero-Tolerance

All member data is synthetic. The population.members table carries a code-level PHI prohibition comment. The user-level CLAUDE.md enforces the rule. This is the trust foundation for the entire platform.

06

Test From Day One

Unit tests for HCC mapping and RAF scoring are verification tests against CMS published examples. Write them before the code, not after. The test suite is the specification. If the test fails, the code is wrong.

07

Small DuckDB Files

Reference tables and scenario outputs should be in separate DuckDB files. Keeps individual files small. No LFS. Close-before-write pattern, retry with exponential backoff. Never track .duckdb files in Git.

08

Execution Over Research

The Repo State Audit (Section 2) and Execution Guide exist so that sessions start with a code editor, not a search tool. If in doubt about current state, check the audit section — don't re-read conversations.
